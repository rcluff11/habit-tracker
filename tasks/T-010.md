# T-010 — Make production deploys safe

## Description
**Priority 1 of 9 (urgent; mostly owner actions, no app code).** Nobody knows what is live: both phase 2 commits are on `origin/main`, and if Netlify auto-publishes, the phase 2 frontend may have been running against a phase 1 backend since about 2026-11-12 (SCOPE-1 = OPS-1). There is no confirmed backup and the rollback has never been tested (OPS-2). The written deploy order can't be followed while Netlify auto-publishes (OPS-3). Nothing alerts when reminders, PocketBase or the VM stop (OPS-4). These come first because every other deploy depends on them, and most are read-only checks the owner can do today.

- **Planned branch:** `chore/deploy-safety` (created when this task moves to in-review).
- **Stakeholder / DRI:** rcluff11 (performs every VM, Netlify and GitHub step; agents never touch production).
- **Closes:** SCOPE-1 = OPS-1; OPS-2 (with DATA-15, part of DATA-8); OPS-3; OPS-4 step 1 (step 2 ships with T-004); SEC-7 answers; DATA-8 answers (disk encryption, log retention); DATA-16 (never edit user data in the admin UI); OPS-10 (deploy previews and env scoping); OPS-11 unit files checked in; OPS-12 (production access log); OPS-14; OPS-16; OPS-17 (unit hardening).
- **Review scope (`AGENTS.md` § 5):** all 9 agents (edits `docs/deployment.md`, `docs/runbooks/`, and `deploy/` config; the CLAUDE.md deploy-order change goes through the docs gate). Architect + DevOps lead.

## Acceptance criteria
1. **Live state recorded (read-only).** The owner runs the checks in `docs/deployment.md` § 7.1 and the answers are recorded in T-003's activity log: (a) the Netlify published deploy's commit, production branch, auto-publish on/off, deploy previews on/off; (b) the manifest `shortcuts` count; (c) the `checkins` endpoint status code; (d) on the VM, `git log -1`, `notch-push` start time, `pocketbase --version`, `node --version`. Every `UNKNOWN` in `docs/` that these answer is replaced with the fact in the same PR.
2. **Interim decision if half-deployed.** If (b) says phase 2 is live and (c) says the schema is missing, the owner chooses, and the choice is recorded: roll the frontend back to the last phase 1 deploy (`cd0f338`) and lock publishing (default, safer while T-004 is open), or leave it. The backend is not deployed early.
3. **Backup and a tested restore.** A `pb_data` backup is taken by a method in `deployment.md` § 7.2, copied off the VM, its SHA-256 recorded; it is restored once into a scratch directory, `PRAGMA integrity_check` returns `ok`, and row counts per collection are recorded. A schedule (7 daily, 4 weekly, off-VM) is set and its location recorded in `runbooks/README.md` "VM facts".
4. **Publishing locked.** Netlify auto-publishing is locked before any merge that needs a backend change; `CLAUDE.md` § Commands deploy order and the `notch-devops` skill say "lock Netlify publishing, back up, then VM, then sender, then publish". `docs/runbooks/deploy-phase.md` matches. (CLAUDE.md edit is made by the owner or with their approval.)
5. **Alerting (no code).** External uptime checks on `https://<pb-host>/api/health` and the site, and a Healthchecks.io `notch-vm` check pinged by a systemd timer only when `notch-push` is active, PocketBase health passes and disk is under 85%. A test alert reaches the owner. The destination is recorded in `runbooks/README.md`.
6. **VM facts filled in.** `runbooks/README.md` "VM facts" records: region and disk (free-tier eligibility), firewall rules, whether PocketBase binds loopback, admin UI exposure and superuser MFA, service users, `push/.env` mode, `PB_URL` value (loopback or not), disk encryption, PocketBase log retention, journald `SystemMaxUse`. Each SEC-7 item that answers "no" on admin UI, firewall/bind or non-root units becomes a BLOCKER task.
7. **Config in the repo.** `deploy/notch-push.service` and `deploy/pocketbase.service` copied from the VM, with OPS-17 hardening (`NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths`, `MemoryMax=200M`, `StartLimitBurst`), plus `deploy/README.md` listing firewall rules and machine type. `push/README.md`'s unit example matches.
8. **Previews and access.** Netlify deploy-preview and `VITE_PB_URL` scoping are recorded; previews are off, or accepted for the owner's own PRs with a note. The production access-log convention (`deployment.md` § 9) is in use, and the "never create or edit user data in the admin UI" rule is in `data-model.md` § 8 and the runbook.

## Out of scope
