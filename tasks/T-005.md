# T-005 — Close server-side data-integrity gaps

## Description
**Priority 3 of 9 (deploy blocker via SDET-10).** The server accepts some writes the app never makes but the API allows: an owner can edit a completion, which re-snapshots its points and can move it to any date (DATA-4 = BE-7, confirmed live); blocks can be saved off the 15-minute grid (DATA-5 = BE-8, confirmed live); `users` rules and auth settings exist only in `pb_data` (SEC-5 = BE-9). The guards that do hold today (cross-user relations on update, anonymous access) have no committed test (SDET-10). This task fixes those in one migration plus hook changes, and the migration carries the relation indexes, because the Data Engineer will block any new migration without them (DATA-1).

- **Planned branch:** `fix/server-data-integrity` (created when this task moves to in-review).
- **Stakeholder / DRI:** rcluff11.
- **Closes:** DATA-4 = BE-7; DATA-5 = BE-8; SEC-5 = BE-9 (with T-8 rate limit, part of DATA-12); DATA-1 (indexes); SEC-9 = BE-12 (`categories` guarded, colour pattern); DATA-9 = BE-13 (real dates); BE-11 (`exists()` fails open); SDET-6 (shared-rule parity); SDET-8 (fixed dates in new tests); SDET-10 (Architect T-1 to T-4, T-6 committed).
- **Review scope (`AGENTS.md` § 5):** full cycle, all 9 agents (schema change, contract change to `completions` update and `blocks` create/update, shared rule added to CLAUDE.md principle 6). Regression-safety check required.

## Acceptance criteria
1. **Pre-deploy data check recorded.** Before the PR is reviewed, the owner runs read-only on the VM: `SELECT count(*) FROM blocks WHERE start % 15 != 0 OR "end" % 15 != 0;` and reads the current `users` collection rules, password minimum and rate-limit settings in the admin UI. The results are recorded in this task's Notes. If the count is non-zero, the migration includes a snap backfill (start down, end up to the grid). Check: the Notes line exists before Round 1.
2. **Completions are immutable.** Given an owner `PATCH` on a completion (`points` or `date`), then the hook returns 400 "A check-off can't be changed. Untick it and tick it again." and, after the migration, the rule layer refuses it too (`updateRule = null`). The record's points and date are unchanged, and a past week's `weekStats` total is unchanged after the task's points are edited. Check: `test:api` cases, failing before, passing after.
3. **15-minute block times.** Given a block create or update with `start=7` or `end=367`, then 400 "Block times must be in 15-minute steps."; `start=0,end=1440` and `start=1425,end=1440` return 200. The server constant `BLOCK_STEP` has a "keep in sync with `STEP` in `src/lib/time.js`" comment, and CLAUDE.md principle 6 lists the pair (owner edit, through the docs gate). Check: `test:api` + a `test:stats` assertion that `STEP === 15`.
4. **`users` rules pinned in a migration.** Given user B, then `users.getList` returns only B, `getOne(A)` returns 404 even with A's `emailVisibility` on, a 7-character password is rejected, and `verified` can't be set on create or update. The migration's `down()` restores the exact values recorded in criterion 1. Whether sign-up stays open is decided by the owner (ADR if it stays open). Rate limiting for `*:auth` and `*:create` is on, set in the migration if the 0.41 JSVM allows it, otherwise documented in `deployment.md`. Check: `test:api` T-1, T-3, T-8.
5. **Relation indexes.** The same new migration adds `user` indexes on `categories`, `blocks`, `tasks`, `rewards`, `push_subscriptions`, `courses`, `course_steps`, `plan_targets`, plus `tasks(block)`, `tasks(step)`, `tasks(category)`, `blocks(step)`, `blocks(category)`, `rewards(category)`, `plan_targets(plan)`, `plan_targets(task)`, `plan_targets(category)` and `completions(user, date)`. `down()` drops exactly these. Check: `test:api` passes on a fresh database; `migrate down` then `up` succeeds locally.
6. **`categories` guarded; colours validated.** `categories` is in `GUARDED`; `color: "red"`, `"#12345"`, `"#1234567"` return 400 on `categories` and `blocks`. Check: `test:api`.
7. **Real dates.** `2026-02-30` is rejected on `blocks.date`, `blocks.recurUntil`, `tasks.date`, `tasks.remindDate` and `completions.date`. Check: `test:api`.
8. **`exists()` fails closed** on any error other than "no rows". Check: code review (not reachable from the API without a database fault).
9. **Committed cross-user guards (SDET-10).** `api-test` covers Architect T-1, T-2 (anonymous `getFullList` on all 11 owned collections and `users`), T-3, T-4 (every cross-user relation on update, and on create for block and reward categories) and T-6. New tests use fixed dates (SDET-8). Check: the cases exist and pass.
10. **Shared-rule parity (SDET-6).** One `api-test` block drives the server with boundary values read from the app modules (`REMINDER_OPTIONS`, `MAX_NUDGES`, `NUDGE_STEP`, `EARLIEST_DAY_END`, `ENERGY_LEVELS`, `EFFORT_LEVELS`, target kinds, `BLOCK_STEP`). Check: changing one side locally makes the suite fail.
11. `contracts.md` (§ 1.2, § 2.3, § 11, § 12 I-10), `data-model.md` and `api.md` are updated in the same PR. All suites green.

- Needs PocketBase running locally.
